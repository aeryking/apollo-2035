# Apollo 2035 性能测试报告

> 所有数据均在**普通浏览器**（非自动化）、**接通电源**、**生产构建**下测得；原始结果见 `docs/bench/real-browser/raw/`，
> 表格由 `tools/report/tables.py` 直接从原始 JSON 生成，避免手抄误差。

## 结论摘要

| 赛题指标 | 结果 |
|---|---|
| 首屏数据展示时间 | 首条路网 **77 ms**、首辆车 **91 ms**（Safari，100 万辆）；Chrome 186 / 199 ms |
| 数据持续加载速度 | 38.7 MB 全部上屏 **0.98 s**（Safari）/ 1.26 s（Chrome），31–40 MB/s；400 万辆时车辆上屏 **368 万辆/s** |
| 数据增量渲染效率 | 每帧上传预算 2.5 ms；800 万辆时持续上传 95.5 MB/s，快照仍保持 0.96 Hz |
| 最大支持渲染规模 | **实时仿真 800 万辆、60 FPS**：Chrome 59.4 FPS 且快照保持 0.96 Hz（每秒更新）；Safari 59.9 FPS（该档未测新鲜度）。纯渲染 800 万辆 Safari 59.9 FPS |
| 地图交互过程中的 FPS | 100 万 / 400 万辆，平移、缩放、旋转、倾斜、近景均 **57.8–60.6 FPS**，0 长任务 |
| 数据加载过程中的 FPS | 34.5–40 FPS（加载持续约 1 s，主要开销为百度引擎初始化，本项目代码占加载期主线程约 4%） |
| CPU 使用率 | 交互期主线程忙碌 0%；每个仿真 Worker 1.2%（100 万辆）～ 6.6%（800 万辆）单核 |
| GPU 使用率 | 车辆图层 7–8 ms/帧（全国视角）、5 ms/帧（城市近景）；关闭垂直同步时整帧中位数 6.2 ms（≈ 154 FPS） |
| 内存占用 | 显存 124 MB（100 万辆）/ 261 MB（400 万辆）；JS 堆 50–185 MB |

## 2. 测试方法

### 2.1 为什么必须用普通浏览器

百度地图会识别自动化环境（`navigator.webdriver`、无头 UA、调试协议连接）并降级：矢量瓦片解码 Worker 收到请求后不再回复，反爬脚本持续高负载。
同一个**不加任何图层的空地图**：自动化浏览器中 0.5–3 FPS，普通 Chrome / Safari 中 60.2 / 60.1 FPS。
因此本报告全部数据都用 `tools/bench/chrome-real.sh`、`tools/bench/safari-real.sh` 以普通用户方式打开页面采集，
页面测完后把结果 POST 回服务器。自动化环境下的早期数据已作废归档（`docs/bench/作废-自动化环境/`）。

### 2.2 测试过程中排除的干扰

| 干扰 | 现象 | 处理 |
|---|---|---|
| 电池电量 ≤ 20% | Chrome 节能模式把帧率锁在 30 FPS（空地图也是 30） | 接通电源后重测，低电量数据全部作废 |
| 后台标签页 | 另一个开着本应用（100 万辆）的标签页持续占用 GPU，同配置帧率从 60 掉到 35–42 | 关闭后重测 |
| 开发服务器 | Vite 运行在 x86 版 Node 上，经 Rosetta 转译，转译进程占用 CPU；且含开发态热更新客户端 | 改测生产构建，由原生 arm64 Python 提供服务 |

### 2.3 测试工具

| 工具 | 用途 |
|---|---|
| `/?bench=1&fleet=N` | 完整测试：加载 → 静止 8 s → 平移 / 缩放 / 旋转 / 倾斜各 6 s → 城市近景 6 s |
| `/?fpsdl=标签&warm=秒` | 帧率探针：预热后采样 8 s，含数据新鲜度（快照换页频率、实际上传量） |
| `/?stress=N` | 纯渲染压测：一次性生成 N 辆静态车辆，不启动仿真 |
| `tools/bench/suite.sh` / `stress-suite.sh` | 浏览器 × 规模对照、纯渲染上限 |
| `tools/bench/rawprof.mjs` | 最小侵入的 CPU 采样（只启用 Profiler 调试域，不触发反爬） |
| `npm run bench:kernel` | WASM / JS 仿真内核对比（Node） |

### 2.4 指标口径

| 指标 | 口径 |
|---|---|
| 首屏时间 | 数据流启动 → 第一条路网线段 / 第一辆车 / 第一个区域面写入显存 |
| 加载速度 | 接入字节 ÷ 启动到全部上屏的耗时；车辆上屏速率 |
| FPS | rAF 帧间隔统计：平均、1% Low、P95、最长帧、卡顿帧（>50 ms）。**屏幕为 60 Hz，rAF 上限即 60 FPS**，60 只说明没有掉帧；性能余量见 §4.3 |
| 数据新鲜度 | 采样窗口内每个 Worker 分片的快照换页次数 ÷ 时长（理想 1 Hz），以及实际上传 MB/s 与理论需要 MB/s |
| CPU | 主线程：长任务占比 + CPU 采样归因；Worker：每秒仿真耗时 ÷ 1000 ms |
| GPU | EXT_disjoint_timer_query 测本项目车辆图层的 GPU 耗时（Safari 不支持，记为 -）；以及分层对照下的帧率差 |
| 内存 | 本项目分配的显存缓冲区按字节记账；JS 堆取 `performance.memory`（Safari 不支持） |

## 3. 首屏与加载

{{T-LOAD}}

**加载阶段主线程归因**（Chrome，100 万辆，生产构建，`rawprof.mjs` 采样）：

| 来源 | 占比 |
|---|---|
| 百度地图引擎初始化（脚本、样式解析、瓦片） | 53.3% |
| 浏览器原生（合成、GPU 命令、布局） | 30.9% |
| 垃圾回收 | 4.7% |
| **本项目全部代码** | **4.2%** |

优化记录：帧率曲线画布在加载时调用 `getBoundingClientRect()`，恰逢百度引擎大量插入 DOM，触发约 0.7 s 强制同步布局（占 7.3%）；改为固定尺寸后消除，本项目占比 10.5% → 4.2%。

### 5.3 WebAssembly 仿真内核

{{T-WASM}}

Node 中的纯内核对比（北京真实路网，逐行等价实现）：50 万辆 2.71×、100 万辆 **3.30×**；位置最大差 0.063 MC 单位（约 5 cm）。
浏览器内加速比较低，部分原因是 WASM 模式每次需要把快照从线性内存拷出再转移给主线程。仿真本身远不是瓶颈（800 万辆时每个 Worker 仅占 6.6% 单核），WASM 的价值在于留出 CPU 余量、支撑更大规模。

## 8. 局限与待补

- 仅在 macOS + Apple M2 上测试；Windows / 独立显卡平台待补测（测试页与回收端可直接在局域网内使用）；
- Safari 不提供 GPU 计时查询与 JS 堆信息，相关列为空；
- 「不限帧率」模式下 CPU 领先 GPU，主线程会在 GL 调用中等待 GPU 进程，故该模式只用于衡量余量，CPU 指标以常规模式为准；
- 800 万辆的显存为估算值（该档未运行完整测试模式）。
