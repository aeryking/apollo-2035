# Apollo 2035 性能测试报告

> 所有数据均在**普通浏览器**（非自动化）、**接通电源**、**生产构建**下测得；原始结果见 `docs/bench/real-browser/raw/`，
> 表格由 `tools/report/tables.py` 直接从原始 JSON 生成，避免手抄误差。

## 结论摘要

| 赛题指标 | 结果 |
|---|---|
| 首屏数据展示时间 | 首条路网 **77 ms**、首辆车 **91 ms**（Safari，100 万辆）；Chrome 186 / 199 ms |

## 2. 测试方法

### 2.1 为什么必须用普通浏览器

百度地图会识别自动化环境（`navigator.webdriver`、无头 UA、调试协议连接）并降级：矢量瓦片解码 Worker 收到请求后不再回复，反爬脚本持续高负载。
同一个**不加任何图层的空地图**：自动化浏览器中 0.5–3 FPS，普通 Chrome / Safari 中 60.2 / 60.1 FPS。
因此本报告全部数据都用 `tools/bench/chrome-real.sh`、`tools/bench/safari-real.sh` 以普通用户方式打开页面采集，
页面测完后把结果 POST 回服务器。自动化环境下的早期数据已作废归档（`docs/bench/作废-自动化环境/`）。

### 2.2 测试过程中排除的干扰

| 干扰 | 现象 | 处理 |
|---|---|---|
| 电池电量 ≤ 20% | Chrome 节能模式把帧率锁在 30 FPS（空地图也是 30） | 接通电源后重测，低电量数据全部作废 |
| 后台标签页 | 另一个开着本应用（100 万辆）的标签页持续占用 GPU，同配置帧率从 60 掉到 35–42 | 关闭后重测 |
| 开发服务器 | Vite 运行在 x86 版 Node 上，经 Rosetta 转译，转译进程占用 CPU；且含开发态热更新客户端 | 改测生产构建，由原生 arm64 Python 提供服务 |

### 2.3 测试工具

| 工具 | 用途 |
|---|---|
| `/?bench=1&fleet=N` | 完整测试：加载 → 静止 8 s → 平移 / 缩放 / 旋转 / 倾斜各 6 s → 城市近景 6 s |
| `/?fpsdl=标签&warm=秒` | 帧率探针：预热后采样 8 s，含数据新鲜度（快照换页频率、实际上传量） |
| `/?stress=N` | 纯渲染压测：一次性生成 N 辆静态车辆，不启动仿真 |
| `tools/bench/suite.sh` / `stress-suite.sh` | 浏览器 × 规模对照、纯渲染上限 |
| `tools/bench/rawprof.mjs` | 最小侵入的 CPU 采样（只启用 Profiler 调试域，不触发反爬） |
| `npm run bench:kernel` | WASM / JS 仿真内核对比（Node） |

### 2.4 指标口径

| 指标 | 口径 |
|---|---|
| 首屏时间 | 数据流启动 → 第一条路网线段 / 第一辆车 / 第一个区域面写入显存 |
| 加载速度 | 接入字节 ÷ 启动到全部上屏的耗时；车辆上屏速率。（演示界面左下角的「加载吞吐」是接入字节 ÷ 传输耗时，截止到最后一个字节到达、不含最后一批上屏，所以数值会高于本表；有缓存时更高） |
| FPS | rAF 帧间隔统计：平均、1% Low、P95、最长帧、卡顿帧（>50 ms）。**屏幕为 60 Hz，rAF 上限即 60 FPS**，60 只说明没有掉帧；性能余量见 §4.3 |
| 数据新鲜度 | 采样窗口内每个 Worker 分片的快照换页次数 ÷ 时长（理想 1 Hz），以及实际上传 MB/s 与理论需要 MB/s |
| CPU | 主线程：长任务占比 + CPU 采样归因；Worker：每秒仿真耗时 ÷ 1000 ms |
| GPU | EXT_disjoint_timer_query 测本项目车辆图层的 GPU 耗时（Safari 不支持，记为 -）；以及分层对照下的帧率差 |
| 内存 | 本项目分配的显存缓冲区按字节记账；JS 堆取 `performance.memory`（Safari 不支持） |

### 4.3 性能余量（关闭垂直同步）

上表第四列以 `--disable-gpu-vsync --disable-frame-rate-limit` 启动 Chrome，每帧画完立即开始下一帧：
100 万辆单帧中位数 6.2 ms，**约 2.7 倍于 60 Hz 预算**；即使是 120 Hz 屏（8.3 ms 预算）中位帧也能跟上。

### 4.4 实时仿真最大规模与数据新鲜度

只看帧率不够：车辆越多，每秒要上传的快照越大，若上传跟不上，帧率依旧 60，但车辆位置会「变旧」。因此同时记录快照换页频率与实际上传量。

### 4.6 规模上限探测（2026-10-16，8 城含支路数据）

在 800 万之后继续加档，每档一个独立的普通 Chrome，测完关闭浏览器、间隔 20 秒；出现报错、崩溃或帧率低于 10 即停止加档。

| 实时仿真车辆 | 平均 FPS | P95 帧时 | 最长帧 | 快照更新频率 | 每 Worker 仿真耗时 | 显存（本项目） | 系统交换区峰值 | 结论 |
|---|---|---|---|---|---|---|---|---|
| 800 万 | **58.1** | 18.3 ms | 52 ms | 0.96 Hz | 63.8 ms/s | 366 MB | 2.8 GB | 流畅，与 §4.4 一致 |
| 2000 万 | 26 | 64.9 ms | 590 ms | 0.15 Hz | 522 ms/s | 916 MB | 5.3 GB | 能跑但不流畅：位置约 7 秒才更新一次，GPU 37 ms/帧 |

GPU 单帧 37 ms（LOD 步长已到上限 15），8 GB 统一内存开始大量换页。1 亿及以上未测：仅车辆显存就需约 4.8 GB，超过本机内存余量。
**本机流畅运行的上限为 800 万辆。** 原始结果：`docs/bench/real-chrome/raw/scale-20261016/`。

## 5. 优化与对照

### 5.1 屏幕密度自适应 LOD（车辆）

| 200 万静态车，全国视角 | LOD 开 | LOD 关 | 提升 |
|---|---|---|---|
| Chrome | **60 FPS**（P95 17.7 ms） | 26.9 FPS（P95 39.5 ms） | 帧率 2.2×，GPU 7.22 ms vs 66.99 ms（9.3×） |
| Safari | **61.1 FPS**（P95 20 ms） | 28.5 FPS（P95 38 ms） | 帧率 2.1× |

### 5.2 着色器与填充优化（分层对照，100 万辆，全国视角）

| 配置 | 优化前 | 优化后 | 手段 |
|---|---|---|---|
| 区域面 | 53.7 FPS | **60.0 FPS** | 省级只描边、地级市填充，避免整片国土重复混合 |
| 100 万静态车 | 51.6 FPS | **60.1 FPS** | 点着色器去掉 `discard` 与 `exp`（TBDR GPU 上代价高）；LOD 步长按「远景约 9 万点」自适应 |
| 路网 | — | 远景 12.8 万段 | 三级 LOD：远景只画高速/快速路（65.8 万 → 12.8 万段） |

（来源：`docs/bench/real-chrome/分层对照-2026-10-15.md`）

### 5.3 WebAssembly 仿真内核

| 轮次 | WASM 内核（每 Worker ms/s） | JS 内核（每 Worker ms/s） | 帧率（WASM / JS） | 快照频率（WASM / JS） |
|---|---|---|---|---|
| 1 | 19.9 | 35.4 | 60.1 / 60.1 | 0.98 / 0.96 Hz |
| 2 | 20 | 33.4 | 60.1 / 60 | 0.98 / 0.96 Hz |
| 3 | 19.2 | 33.8 | 60 / 60 | 0.98 / 0.98 Hz |
| **平均** | **19.7** | **34.2** | — | — |

浏览器内加速比 **1.74×**（Chrome，200 万辆，6 个 Worker）。

Node 中的纯内核对比（北京真实路网，逐行等价实现）：50 万辆 2.71×、100 万辆 **3.30×**；位置最大差 0.063 MC 单位（约 5 cm）。
浏览器内加速比较低，部分原因是 WASM 模式每次需要把快照从线性内存拷出再转移给主线程。仿真本身远不是瓶颈（800 万辆时每个 Worker 仅占 6.6% 单核），WASM 的价值在于留出 CPU 余量、支撑更大规模。

## 8. 局限与待补
