# Apollo 2035 技术方案

> 基于百度地图 JSAPI 4.0 WebGLLayer 的海量空间数据流式高性能渲染

## 1. 场景与目标

**场景**：2035 年全国无人驾驶出行运营中枢。萝卜快跑 2026 年已在 20 余座城市全无人运营，本方案把这一业务向后推演十年：
全国数百万辆无人车同时在线，每辆车每秒上报一次定位（真实车联网的典型节拍）。

这是一个典型的「海量空间数据、持续数据更新、高频地图交互」工业场景，与赛题列举的设备点位监控、物流轨迹、管网态势同构：

| 本项目 | 对应的工业场景 |
|---|---|
| 车辆（点，1 Hz 状态更新） | 设备点位监控、人员定位 |
| 路网（线，流动光效） | 管网运行态势、物流干线 |
| 区域 / 需求热度（面，按值着色、3D 柱） | 能源消耗分布、园区分区 |
| 生命通道（事件联动） | 园区安防调度 |

**目标**：数据持续加载期间用户无需等待即可看到逐步生成的结果；渲染规模达到百万级以上；后台持续处理数据时地图交互保持流畅。

## 2. 总体架构

```
                         ┌────────────────────── 主线程 ──────────────────────┐
 HTTP 分块数据 ─┐        │                                                    │
               │        │  上传调度器（每帧 2.5 ms 预算）── 显存（三缓冲）     │
 ┌─ Worker ×N ─┴──────┐ │        ▲                         │                  │
 │ fetch 流 → 帧解析   │─┼── 可转移 ArrayBuffer（零拷贝）    ▼                  │
 │ WASM 仿真 → 快照    │ │                     WebGLCustomLayer.onRender       │
 └────────────────────┘ │                      点 / 线 / 面 / 3D 柱 / 事件     │
 ┌─ Worker ───────────┐ │                     （实例化绘制，GPU 插值）         │
 │ GeoJSON 流 → earcut │─┤                                                    │
 └────────────────────┘ │   百度地图 JSAPI 4.0（共享同一 WebGL 上下文）          │
 ┌─ Worker ───────────┐ │                                                    │
 │ 需求预测网格         │─┘                                                    │
 └────────────────────┘ └────────────────────────────────────────────────────┘
```

**分工原则**：主线程不做任何解析和逐要素计算，只做两件事 —— 按帧时间预算把数据写进显存、发出绘制命令。
「获取 → 解析 → 计算 → 上传 → 绘制」五段全部异步化，彼此通过可转移对象（Transferable）衔接。

## 3. 百度 WebGLLayer 接入：实测结论与踩坑

以下全部为本机实测（详见 [`00-平台实测.md`](00-平台实测.md)），其中第 3、4 条是官方文档未写明、但决定成败的行为。

1. **必须使用 JSAPI 4.0**：`api?v=4.0&type=webgl`。默认的 GL 1.0 版本不导出 WebGLLayer 体系。
2. **类族**：`WebGLCustomLayer → WebGLLayer(基类) → Object`，基类未对外导出。本项目所有图层封装在 `layers/base.js`，以 `WebGLCustomLayer` 为载体，在 `onRender` 中自建缓冲、自建着色器程序完成绘制。
3. **MVP 矩阵只在「图层程序使用了 `u_mvpMatrix`」时才注入**。若占位着色器没有用到它，`ctx.getMVPMatrix()` 恒为全零，所有顶点塌缩到一点、画面空无一物且无任何报错。对策：占位着色器显式使用 `u_mvpMatrix`。
4. **安全模式只还原框架自己的状态缓存，不还原真实 GL 绑定**。底图渲染器依赖缓存跳过重复绑定，我们若修改 `ARRAY_BUFFER` / 程序 / VAO 而不还原，下一帧底图会读到我们的缓冲区，整屏空白。对策：每帧前后保存/还原真实绑定（均为客户端状态查询，不引起 GPU 同步）。
5. **`unsafeGL` 模式下改 framebuffer/viewport 会擦掉底图**，故使用安全模式；混合与深度测试通过官方 `renderState` 设置；全部绘制直接画在地图的帧缓冲上，不使用离屏 FBO。
6. **坐标系**：MVP 作用于「百度墨卡托相对 `BASE_MC` 的偏移」，`BASE_MC = [12069475.28, 3929271.17]` 为固定常量，不随平移漂移。百度墨卡托（BD09MC）是分纬度带多项式而非标准 Web Mercator，本项目从官方运行时移植了正反两套系数表（`core/projection.js` 的 `ll2mc` / `mc2ll`），Worker 中无需 BMap 也能算出与底图逐像素对齐的坐标；反投影用于镜头跟随（往返误差 ≤ 0.12 m）。实测平移 / 缩放 / 旋转 / 倾斜下偏差 < 0.5 px。
7. **精度**：中国范围内相对坐标最大约 3.3×10⁶，float32 精度约 0.25 m，zoom 19 下 < 0.5 px，无需高低位拆分。

## 4. 流式数据处理模块

### 4.1 数据格式：自描述二进制帧

`stream/binary.js`：

```
文件头 32 B：magic 'A35S' | 版本 | 类型 | 记录数 | 4 个 float 元信息
帧：type(u8) | len(u32) | payload
```

- 帧自描述：拿到一个完整帧即可独立解析，**不需要等整个文件下载完**；
- 解析器支持任意切分的字节流（逐字节喂入的单元测试通过），半包留待下一块；
- 几何已预先投影为图层坐标并打包成 GPU 可直接使用的结构化数组，解析即视图（`subarray`），零中间对象。

### 4.2 分块与调度

- **分块打包**（`tools/build-packs.mjs`）：375 座城市合并为 19 个约 3 MB 的区域数据块。逐城 490 个小请求实测吞吐仅 1.4 MB/s，合并后单流读取，下载与解析流水线重叠。
- **块内顺序**：按城市人口降序 —— 最重要的数据最先到达。
- **视野优先调度**（`stream/lineFeed.js`）：未开始的块按「到视野中心距离 / 城市重要度」排序，地图移动结束后重排；用户看哪里，哪里先出数据。
- **负载均衡**（`sim/fleet.js`）：以数据块为单位做贪心装箱，按权重均衡分配给各仿真 Worker，每个 Worker 只下载、解析自己负责的块。

### 4.3 三条流水线

| 流水线 | 获取 | 解析 / 计算 | 交付 |
|---|---|---|---|
| 车辆（点） | 仿真 Worker `fetch` 流读取路线池块 | 每解析出一个城市帧立即生成该城车辆；WASM 内核每秒推进位置并打包 16 B/车快照 | 快照 ArrayBuffer 转移给主线程 |
| 路网（线） | 流式 Worker 读取路网块 | 逐帧拆出城市线段数组 | 线段数组转移，主线程排队上传 |
| 区域（面） | 区域 Worker 流式读取 NDJSON | 逐行 `JSON.parse` → GCJ02→BD09→墨卡托 → earcut 三角化 | 每满 6 万顶点转移一批 |

### 4.4 增量上传：时间预算 + 三缓冲 + 缓冲区孤立

- **时间预算**：每帧上传不超过 2.5 ms（可调），按 16K 条记录切块，每块后检查预算；数据再多也不会让单帧超时。
- **队列而非覆盖**：数据到达快于上传时排队，绝不丢弃（早期版本直接覆盖未完成任务，实测丢失 94% 路网线段，已修复）。
- **三缓冲换页**（车辆）：「上一帧 / 下一帧 / 正在写」三块缓冲轮换，写入的永远是约 1 秒前就已不再被 GPU 读取的那一块，既不撕裂、也不会触发 CPU 等 GPU 的同步。因此无需缓冲区孤立（orphaning，保留 `?orphan=1` 开关做对照）。实测 100 万辆、每秒 14.8 MB 快照，上传只占主线程 3.4 ms/秒。
- **快照相位错开**：N 个仿真 Worker 的 1 Hz 节拍错开 1/N 秒，上传负载在一秒内均匀分布，而不是挤在同几帧里。
- **追加写入**（路网 / 区域）：只写尚未被绘制的区间，与 GPU 读取不冲突。

### 4.5 缓存

- 路线池常驻仿真 Worker（车辆状态与路线数据放在 WASM 线性内存，JS 侧以 TypedArray 视图零拷贝读写）；
- 主线程不保留快照副本：快照上传完即释放，显存是唯一的数据驻留处；
- 静态数据块走浏览器 HTTP 缓存，二次打开命中缓存。

## 5. WebGL 高性能渲染模块

### 5.1 车辆（点）—— `layers/vehicle.js`

- **GPU 快照插值**：仿真每秒只产出一次快照，顶点着色器在「上一秒 / 下一秒」两块缓冲之间按时间 `mix`，画面 60 fps 连续运动，CPU 不参与逐帧计算。新出现的车辆带 `born` 标记，跳过插值避免从原点飞入。
- **16 字节紧凑记录**：`float32 x, y, angle` + `u8 速度, 状态, born, 车长`，后 4 字节以 `UNSIGNED_BYTE` 归一化属性直接读取。百万车三缓冲仅 46 MB 显存。
- **双模式**：远景用点精灵（一个顶点一辆车）；z ≥ 13.5 切换为实例化四边形，着色器内用胶囊距离场画出有朝向的车身，最小屏幕尺寸随缩放平滑过渡。
- **视锥剔除 + 区间合并**：Worker 上报每座城市在实例缓冲中的区间与包围盒；绘制前剔除视野外城市并合并相邻区间。北京 z16 时 30 万车中只提交 4,276 辆。视口范围按相机矩阵变化缓存（`map.getBounds()` 每帧调用实测占主线程 7%）。
- **屏幕密度自适应 LOD**：全国视角下成千上万辆车落在同一像素，在分块渲染（TBDR）GPU 上反复混合代价极高。利用「属性步长」每 k 辆取 1 辆绘制，k 按「远景约 9 万点 / 中景约 18 万点」的预算自适应（上限 15：WebGL1 步长 ≤ 255 字节，16 B × 15 = 240 B）。远景不做亮度补偿 —— 城市灯火由 §5.6 的光晕图层负责，单车点只做「星尘」质感，避免叠加饱和成一片白。真实浏览器中 200 万车：Chrome 26.9 → **60 FPS**（GPU 67.0 → 7.2 ms），Safari 28.5 → **61.1 FPS**。
- **无分支点着色器**：去掉 `discard` 与 `exp`，用二次多项式衰减近似「亮核 + 辉光」—— 在 TBDR GPU 上 `discard` 会让整块 tile 失去隐藏面消除优化。两项合计：100 万静态车（Retina）51.6 → **60.1 FPS**。
- **WebGL1 无 baseInstance**：实例化绘制的区间起点通过属性指针字节偏移实现。

### 5.2 路网（线）—— `layers/road.js`

- 每条线段一个实例，顶点着色器沿法向把线段扩成四边形，线宽以像素为单位恒定、不随缩放变粗；
- 道路等级配色（高速暖色、主干冷色），沿程里程驱动的流光完全由 `u_time` 计算，CPU 零开销；
- **三级 LOD**：上传时按道路等级分到三块缓冲 —— 高速/快速路（12.8 万段，始终绘制）、主干道（22.2 万段，z ≥ 7）、次干道及以下（30.7 万段，z ≥ 9）。全国视角下支线远小于 1 像素，不画也看不出差别，却省掉 80% 的细碎三角形；
- 每级 1 次 Draw Call，最多 3 次。

### 5.3 区域（面）—— `layers/zone.js`

- Worker 内三角化后的三角网直接增量写入大缓冲，填充 + 描边 2 次 Draw Call；
- 523 个省市面、48.9 万填充顶点，下载到哪画到哪；
- 省级面只出描边（地级市面已铺满全国，再填一遍会让整片国土重复混合）：53.7 → **60.0 FPS**。

### 5.4 需求预测（3D 面）—— `layers/hex.js`

- 一个六棱柱模板（54 顶点）供全部格子共享；每格只有「中心 + 数值」两个实例属性；
- 数值双缓冲，高度在顶点着色器中按时间插值，柱子平滑升降；每秒只更新约 10 KB；
- 开启深度测试（经 `renderState`），柱体遮挡关系正确。

### 5.5 生命通道 —— `layers/event.js` + 仿真 Worker

- Worker 中对北京车辆做「到通道折线距离」的空间查询（只查救护车前方 1.6 km 内的线段），命中者减速停车、标记为让行状态（亮白色，压在红色通道上依然醒目）并向路外侧平移；
- 救护车路线按「端点直线距离 ≥ 6 km 且穿过市中心附近」挑选 —— 按路程长度挑选会选中走一段又原路折返的路线，在屏幕上缩成一小截（实测踩坑）；
- 通道线按「沿程里程与救护车位置」分段着色，前方让行段脉冲发光；救护车位置在主线程按速度外推，每帧平滑前进；
- 镜头：地图转向救护车前进方向（通道向屏幕深处延伸），并经反投影逐帧跟随。转向必须用无动画方式，否则会被逐帧 `setCenter` 打断。

### 5.6 城市光晕（聚合层级）—— `layers/glow.js`

全国视角里一座城市只占几个像素，单车画得再多也只是一团饱和的白点。这一层为每座城市画一个柔和光团：
大小 ∝ √人口，颜色随全国载客率在「空驶青 / 载客金」之间变化，心跳式脉动；**城市数据流式到达的那一刻闪光点亮** —— 「边下载、边显示」直接可见。
375 个实例 1 次 Draw Call，城市点亮时只写 4 字节；z ≥ 7 起淡出，交给单车图层。

### 5.7 城际流线 —— `layers/flow.js`

引力模型 OD（强度 ∝ 人口ᵢ × 人口ⱼ / 距离^1.6，取最强的若干城市对，并保证每座大城市连到最近的两座）。
每条 OD 为一条二次贝塞尔弧，CPU 一次性细分为 40 段，之后只靠 `u_time` 驱动光点沿弧线流动；约 1 万段 1 次实例化绘制，z ≥ 6.5 起淡出。

### 5.8 Draw Call 汇总

| 图层 | Draw Call |
|---|---|
| 车辆 | 每个仿真 Worker 1 次（相邻城市区间合并后），通常 4–6 次 |
| 路网 | 1–3（按缩放级别启用的 LOD 级数） |
| 区域面 | 2（填充 + 描边） |
| 城市光晕 / 城际流线 | 各 1（全国视角） |
| 需求柱 | 1（第三幕） |
| 事件 | 2（第四幕） |
| **合计** | **约 11 次绘制全部要素**（实测全国视角 11 次） |

## 6. WebAssembly 仿真内核

`wasm/sim/src/lib.rs`（Rust，`no_std`，产物 2 KB）：

- 车辆状态数组（SoA）与路线池全部放在 WASM 线性内存，JS 侧以 TypedArray 视图读写，**零拷贝共享**；
- 导出 `step`（状态机 + 沿路线推进）与 `snapshot`（二分定位线段 + 插值 + 打包），与 JS 版逐行等价；
- 内存增长会使旧视图失效，每次分配后重建视图；
- 加载失败自动回退 JS 内核（`?wasm=0` 可强制）。

实测（Node，北京真实路网，同一份数据）：

| 车辆数 | JS（ms/步） | WASM（ms/步） | 加速比 |
|---|---|---|---|
| 50 万 | 47.7 | 17.6 | 2.71× |
| 100 万 | 115.5 | 35.0 | **3.30×** |

两版输出位置最大差 0.063 MC 单位（约 5 cm），朝向最大差 0.0002 rad。

浏览器内（Chrome，200 万辆，6 个 Worker，同条件背靠背三轮）：WASM 每 Worker 19.7 ms/s，JS 34.2 ms/s，**1.74×**。
浏览器内加速比低于 Node，部分原因是 WASM 模式每次需要把快照从线性内存拷出再转移。仿真本身远不是瓶颈（800 万辆时每个 Worker 仅占 6.6% 单核），WASM 的价值在于留出 CPU 余量、支撑更大规模。

## 7. 主线程负载控制与验证方法

- **CPU Profile 驱动优化**：采集主线程调用栈热点，依次定位并消除了「每帧 `getBounds`」「上传 GPU 同步卡顿」「HUD 每帧写 DOM」「加载时强制同步布局（约 0.7 s）」四处开销；优化后加载阶段本项目代码只占主线程约 4%，交互期 0 长任务。
- **HUD 节流**：DOM 文本 4 Hz 更新；帧率曲线画布固定尺寸，不读取页面布局。
- **数据新鲜度监测**：只看帧率不够 —— 上传跟不上时帧率依旧 60，车辆位置却会「变旧」。测试探针同时统计每个分片的快照换页频率与实际上传量（800 万辆时仍为 0.96 Hz）。
- **测试环境说明**：百度地图会识别自动化环境（`navigator.webdriver`、无头 UA、调试协议连接）—— 矢量瓦片解码 Worker 收到 `loadTileData` 后不再回复，反爬脚本持续高负载，空地图只有 0.5–3 FPS；同一页面在普通 Chrome / Safari 中为 60 FPS。因此所有性能数据都用 `tools/bench/chrome-real.sh`、`safari-real.sh` 在普通浏览器中采集（Chrome 用临时配置目录；结果由页面 POST 回服务器），CPU 采样只启用 Profiler 一个调试域（`tools/bench/rawprof.mjs`）。详见 [`性能测试报告.md`](性能测试报告.md)。

## 8. 已知限制与后续

- 合成路网城市的道路为程序生成的环放结构，仅 6 座城市使用 OSM 真实路网；
- 需求预测为可解释的热点模型，非训练所得；
- WebGL1 无 `copyBufferSubData`，缓冲扩容需重建 —— 本方案以清单预估容量一次分配规避；
- 后续可将快照量化为 int16（相对城市原点）把带宽再减半，并引入 OffscreenCanvas 预处理纹理类数据。
